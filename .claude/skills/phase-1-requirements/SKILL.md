# フェーズ1: 要件定義

## 目的

コードを1行も書く前に、「何を作るか」を文書として確定させる。タイクーンゲームの面白さは
数値設計とルールに宿るため、ここを曖昧にしたまま実装に進むと後工程の手戻りが大きい。

## 進め方

1. `phase/1-requirements` ブランチを作成する(git-workflowスキル参照)
2. 以下の4項目について、ユーザーとの会話からわかる情報を最大限拾いつつ、不明点は
   質問するか、妥当なデフォルト案を提示して確認を求める(全部を質問攻めにしない。
   仮案を出して「これでよければ進めます」と確認する方が手数が少ない)
3. `docs/requirements.md` を作成する
4. 完了条件を満たしたらコミット・プッシュし、サマリーを提示してユーザーの承認を待つ

## 確定させるべき4項目

### 1. 資源(コイン)
- 資源の種類は単一(コインのみ)か複数か
- 自動収集の基本レート、レート上昇の仕組み(施設強化との関係)
- オフライン時間中の収集をどう扱うか(全額計算/上限あり/計算しない)

### 2. 施設
- 施設の種類(例: 3〜5種程度から開始し、後から追加できる設計にする)
- 各施設が何に効果を与えるか(コイン生成レート上昇/豚の出現率上昇 等)
- レベルアップのコスト曲線の方向性(指数関数的増加が定番)

### 3. 豚(コレクション要素)
- 豚を「集める」とは具体的に何を意味するか(例: 一定確率で出現しタップで捕獲/コインを一定額貯めると1匹入手/施設のレベルアップ報酬)
- 豚の種類・レア度は設けるか
- 豚を集めることによるゲームプレイ上の見返り(コイン生成ボーナス等)はあるか、それとも収集自体が目的か

### 4. MVPスコープの境界線
- 今回のフェーズ1〜5で「作らないもの」を明記する(例: プレステージ/周回要素、実績システム、サウンド、マルチプレイ等)
- スコープ外にした理由を一言添える(後で「なぜ含めなかったか」を思い出せるように)

## 成果物フォーマット (docs/requirements.md)

```markdown
# 要件定義

## 資源
...

## 施設一覧
| 施設名 | 効果 | 初期コスト | コスト成長率 |
|---|---|---|---|

## 豚の収集ルール
...

## MVPスコープ外(今回やらないこと)
- 項目: 理由
```

## 完了条件(Definition of Done)

- [ ] 4項目すべてが `docs/requirements.md` に具体的な数値・ルールとして記載されている(「未定」が残っていない)
- [ ] MVPスコープ外の項目が明記されている
- [ ] コミット・プッシュ済み

## 次フェーズへの引き継ぎ

`phase-2-state-design` は本フェーズの `docs/requirements.md` を入力として、
TypeScriptの型定義とZustandストアのスキーマを設計する。要件が曖昧なまま次フェーズに
進むと型設計がやり直しになるため、承認前に「これで型設計に進んで問題ないか」を
意識してレビューを促すこと。
