# フェーズ5: テスト・バランス調整

## 目的

MVPとして触ったときに「気持ちよく成長を感じられるか」を検証し、必要な数値調整を行う。
この段階の変更は基本的に `src/logic/constants.ts` の数値調整に閉じ、ロジックの構造変更は
最小限に留める(構造変更が必要なほど大きな問題が見つかった場合はユーザーに相談する)。

## 前提条件

`phase-4-ui-implementation` が承認済みで、一通り操作できる状態であること。

## 進め方

1. `main` から `phase/5-testing-balance` ブランチを作成する
2. 以下のエッジケースを確認し、問題があれば修正する
   - 長時間(例: 24時間以上)放置した場合のオフライン計算が破綻しないか
   - 数値が非常に大きくなった場合の表示崩れ・計算誤差(浮動小数点精度)
   - 施設レベルが0の状態、最大レベルに達した状態での挙動
   - 豚のコレクションが空の状態、全種類集め終えた状態での表示
3. 数値パラメータ(`constants.ts`)を調整するたびに理由をコミットメッセージに残す
   ```
   fix(balance): 施設Aのコスト成長率を1.15→1.12に調整(中盤の停滞感を緩和)
   ```
4. 未解決の課題や意図的に見送った改善は `docs/known-issues.md` に一覧化する
5. 調整が一段落したらコミット・プッシュし、サマリーを提示して承認を待つ

## バランス調整の考え方

- 「なぜその数値にしたか」を毎回言語化する(勘だけで変更しない)。判断基準の例:
  - 初回アップグレードは「数秒〜数十秒で手が届く」体感を目安にする
  - コスト成長率は施設ごとに差をつけ、序盤・中盤・終盤で主力施設が切り替わるようにする
  - 豚の収集はランダム性がある場合、極端な連続ハズレ/連続当たりが起きにくいよう
    保証機構(天井システム等)の要否を検討する
- 数値調整はテストで担保しにくい領域なので、`docs/balance-notes.md` に
  「この数値にした理由」と「試した他の値との比較」を記録し、後から再調整しやすくする

## 完了条件(Definition of Done)

- [ ] エッジケース4項目を確認し、致命的な破綻がないことを確認した
- [ ] 数値調整の理由が `docs/balance-notes.md` に記録されている
- [ ] 未解決課題が `docs/known-issues.md` に一覧化されている
- [ ] 全ユニットテストが通過している
