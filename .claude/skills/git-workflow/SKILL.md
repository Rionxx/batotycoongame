# Git ワークフロー(フェーズブランチ運用)

## ブランチ戦略

- 1フェーズ = 1ブランチ。命名規則は `phase/<番号>-<英語スラッグ>`
  - 例: `phase/1-requirements`, `phase/2-state-design`, `phase/3-core-logic`
- 新しいフェーズを始める前に、必ず最新の `main` から分岐する
  ```bash
  git checkout main
  git pull origin main
  git checkout -b phase/3-core-logic
  ```
- `main` ブランチへの直接コミット・直接pushは行わない

## コミット規約

Conventional Commitsに従う。プレフィックスの目安:

| プレフィックス | 用途 |
|---|---|
| `feat:` | 新機能・新規実装 |
| `fix:` | バグ修正 |
| `test:` | テスト追加・修正 |
| `docs:` | ドキュメント(requirements.md等)の作成・更新 |
| `refactor:` | 挙動を変えないコード整理 |
| `chore:` | 設定ファイル等の雑務 |

例:
```
feat(logic): 資源自動加算のtick処理を実装
test(logic): 施設アップグレードのコスト曲線にユニットテストを追加
docs(requirements): 豚の収集条件を確定
```

**やってはいけないこと**: 複数の意味的に無関係な変更を1コミットにまとめる。「とりあえず全部まとめてコミット」は禁止。

## コミット・プッシュの粒度

- 1つの意味のある作業単位が終わるごとにコミットする(ファイル全部が完成するまで待たない)
  - 良い例: 型定義ができた→コミット。ストアの骨組みができた→コミット。永続化処理ができた→コミット
  - 悪い例: フェーズ全体が終わるまで無コミットで進め、最後に巨大な1コミットにする
- コミットしたら基本的にその都度 `git push origin <ブランチ名>` する。プッシュを溜めない
  - 理由: セッションが途中で切れても作業が失われないようにするため、かつユーザーがGitHub側から進捗を随時確認できるようにするため
- 初回プッシュ時は `-u` を付けてリモート追跡を設定する
  ```bash
  git push -u origin phase/3-core-logic
  ```

## フェーズ完了時のマージフロー

1. フェーズの成果物をユーザーに提示し、承認を得る(CLAUDE.mdの承認ゲート参照)
2. 承認が得られたら、最新の状態をpushしたことを確認する
3. `main` にマージする(ローカルで完結する小規模プロジェクトなので、squash mergeでも通常mergeでも可。ユーザーに好みを確認してよい)
   ```bash
   git checkout main
   git pull origin main
   git merge --no-ff phase/3-core-logic
   git push origin main
   ```
4. 次フェーズのブランチを新規作成して作業を継続する

## 禁止事項

- force push(`git push -f`)は行わない
- 承認前のフェーズブランチをmainにマージしない
- コミット履歴の書き換え(rebase -i によるhistory改変)はユーザーの明示的な指示がない限り行わない
