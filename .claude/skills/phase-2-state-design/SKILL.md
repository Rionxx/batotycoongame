# フェーズ2: 状態設計

## 目的

「何を作るか」(要件)を「どう表現するか」(データ構造)に変換する。ここでの設計判断が
コアロジック・UIの両方の実装しやすさを左右するため、コードを書き進める前に構造を固める。

## 前提条件

`docs/requirements.md` が承認済みであること。未承認の場合は先にphase-1-requirementsへ戻る。

## 進め方

1. `main` から `phase/2-state-design` ブランチを作成する
2. `docs/requirements.md` の内容を型に落とし込む(`src/types/game.ts`)
3. Zustandストアの骨組みを作る(`src/store/gameStore.ts`)。**この段階ではロジック(計算処理)は実装しない。** 状態の形と初期値、アクションのシグネチャ(関数の型)だけを定義する
4. 永続化(localStorage)のキー設計・保存タイミングの方針を決める
5. 設計判断の理由を `docs/state-design.md` に記録する(なぜこの形にしたか、後から見て意図がわかるように)
6. コミット・プッシュし、サマリーを提示して承認を待つ

## 設計時の判断基準

- **正規化 vs ネスト**: 施設や豚の数が少ない(数個〜数十個程度)うちはネストした配列で十分。将来数百件規模になる見込みがあるなら正規化(IDをキーにしたオブジェクト)を検討する
- **1ストア vs 複数ストア**: 単一ゲームなのでZustandストアは1つに統合し、セレクタで関心事を分離する方針を基本とする(過剰な分割は避ける)
- **ロジックとストアの境界**: ストアのアクションは「状態をどう更新するか」の入口のみを持ち、実際の計算式(コスト曲線、資源加算式)はフェーズ3で `src/logic/` に実装する。ストアからロジック関数を呼び出す形にし、ロジックをUIやストアの実装から独立させる

## 成果物

- `src/types/game.ts` — Resource, Building, Pig, GameState などの型定義
- `src/store/gameStore.ts` — Zustandストアの骨組み(状態初期値 + アクションの型のみ、中身はTODOコメントで良い)
- `docs/state-design.md` — 設計判断の記録

## 完了条件(Definition of Done)

- [ ] `docs/requirements.md` の全要素(資源・施設・豚・MVPスコープ)が型に反映されている
- [ ] `any` 型を使っていない
- [ ] ストアのアクションのシグネチャが定義されている(実装は未着手でよい)
- [ ] 永続化キーの命名規則が決まっている
- [ ] `docs/state-design.md` に判断理由が記録されている

## 次フェーズへの引き継ぎ

`phase-3-core-logic` はこのフェーズで定義した型とストアの骨組みを前提に、
実際の計算ロジックを実装する。型が確定していないと計算式の実装がやり直しになるため、
承認前にユーザーへ「この型構造でコアロジックに進んでよいか」を確認すること。
